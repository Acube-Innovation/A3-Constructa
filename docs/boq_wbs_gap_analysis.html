BOQ → WBS → Item Mapping

Gap analysis: client requirement vs A3 Constructa as built
Masiha Services SARL  •  ERPNext v15 + A3 Constructa  •  September 2026

The structure the requirement describes is already in the system: a Cost Head tree, a WBS tree, Cost Codes, a BOQ with an approval workflow, WBS Allocations, and WBS / Cost Code tags carried from Material Request through Purchase Order and Purchase Receipt to Stock Entry. The gaps are in the rules around that structure. Almost nothing is enforced, no report rolls up the WBS tree, and invoice costs never reach a WBS.

The requirement, step by step

Requirement stepStatusWhat the system does today, and the gap
Create project + load initial BOQ; keep contract value and cost budget separate PARTIAL The BOQ holds a quantity × rate and an approved quantity × approved rate. Both are cost figures. There is no contract (selling) value and no link to the customer order. The BOQ header totals only the first amount, not the approved budget.
01  Initial cost heads: broad allowances, no item codes needed MISSING Cost Heads exist as a tree, but every BOQ line and every WBS Allocation line requires an item code. A lump-sum allowance for "Architectural" or "MEP" cannot be recorded before items are chosen.
02  Develop work packages; keep the original BOQ reference PARTIAL The WBS tree can model Architectural → Flooring → WBS A, but a node has no type (cost head, work package or WBS) and its cost head is not checked against its parent. A WBS has no BOQ reference. The BOQ-line link on a WBS Allocation is read-only with no way to pick it on the form.
03  Define scope + location (e.g. ground floor, first floor) MISSING A WBS has no location or floor field and no scope description. Location exists only on the Project.
04  Map approved items to budget lines: one item code → many WBS PARTIAL The same item can be allocated to WBS A (600 m²) and WBS B (400 m²) in two WBS Allocations. Over-allocation is not blocked, allocations are never approved or locked, and draft allocations count as budget. Details on page 2.
PR → Approval → PO → Receipt → Transfer / Consumption, each line keeping Project + WBS + Cost Code + Item + Qty PARTIAL The tags exist on Material Request, Purchase Order, Purchase Receipt and Stock Entry lines and carry forward automatically. There is no Material Request approval, no check against the WBS budget, and the tags stop at the Purchase Invoice.
Report: WBS → Work Package → Cost Head → Project, with commitments, stock and consumption shown separately PARTIAL Budget vs WBS, Budget vs Commitment, Cost Code Wise Costing and Cost to Complete exist. None of them rolls up the tree, stock on hand is not shown, and invoiced actuals read zero.

Detailed findings

Budget allocation (step 04)

#GapEffect on the flooring example
A1Over-allocation is not blocked The system works out the remaining balance of a BOQ line but never stops a save. 600 + 400 + 300 m² against a 1,000 m² line saves with a negative balance.
A2Balance is measured against the BOQ quantity, not the approved quantity Where the approved quantity is lower than the BOQ quantity, the balance overstates what is left to allocate.
A3WBS Allocation cannot be submitted or approved Every report counts draft allocations as budget. An unreviewed draft moves the budget immediately.
A4A Cost Code is tied to a single WBS Using one flooring cost code on both WBS A and WBS B, as the requirement shows, conflicts with the master.
A5No split view or split action There is no "get lines from BOQ" or "split across WBS" action, and no screen showing one item's allocations across all WBS.

Procurement and stock chain

#GapEffect on the flooring example
T1Purchase Invoice lines carry no WBS, Cost Head or Cost Code The 1,000 m² tile invoice cannot be traced back to the 600 / 400 split. The chain breaks at billing.
T2No Material Request approval The only workflow is BOQ Approval. The Approval Matrix records rules but nothing enforces them.
T3Requests are not checked against the WBS budget A request for tiles on WBS A is not checked for whether the item is allocated there or whether the quantity is within the 600 m². WBS is not filtered by project, and Cost Code is not filtered by WBS.
T4Consolidated PO only as separate lines A PO line holds one WBS, so the order is two lines (600 + 400) rather than one 1,000 m² line with a split. On a partial receipt the storekeeper has to choose which line to receive against.
T5Procurement Plan is standalone It does not read from WBS Allocations and cannot create a Material Request.

Reporting

#GapEffect on the flooring example
R1No roll-up through the tree Reports group by the exact WBS or Cost Head on each record. "Flooring" does not show WBS A + WBS B together, and "Architectural" does not show Flooring + Painting + Doors & Windows.
R2Invoiced actuals never reach a WBS The general ledger has WBS and Cost Code fields, but nothing fills them. Invoice and journal costs read zero in Budget vs WBS and Budget vs Cost Code.
R3Stock on hand is not shown separately Material received but not yet issued is not reported per WBS. Transfers to site are ignored; only material issues count as consumption.
R4No quantity view Reports show amounts only. Nothing shows m² allocated, requested, ordered, received and consumed per WBS and item.
R5BOQ vs Consumption adds up different items It groups by cost code only, so tiles (m²), adhesive (kg) and grout (kg) under one cost code are summed into one meaningless quantity.

Implementation rules

Rule from the requirementStatusToday
Parent budget = child allocations + unallocated balance. Do not add levels together. MISSING Budget can be allocated to a parent node and to its children at the same time. There is no unallocated-balance figure, so a cost-head allowance plus its child allocations would be double-counted.
One WBS can use many items: tiles, adhesive, grout, installation. COVERED A WBS Allocation holds any number of item lines, each with its own cost code, rate and amount.
Consolidated PO of 1,000 m² keeping the 600 / 400 split and partial-receipt links. PARTIAL Works as two PO lines, and receipts carry the WBS from the PO line. A single line with a split is not possible, and invoices lose the split (T1, T4).
Preserve budget revisions. PARTIAL The BOQ has a revision number typed by hand and can be amended. WBS Allocations are edited in place, with only the change log as history. There is no original / revised / current budget comparison. A revision entered as a new BOQ rather than an amendment is counted twice.

Recommended fixes, in order

#ChangeTypeCloses
1 Make WBS (and Cost Code) an ERPNext Accounting Dimension STANDARD T1, R2, and budget control by WBS through the standard Budget doctype. The existing custom WBS fields must be migrated to the dimension fields first.
2 Make WBS Allocation submittable and block over-allocation against the approved quantity CUSTOM A1, A2, A3, and the revision history for allocations.
3 Allow allowance lines without an item code; add node type, location and BOQ reference to WBS CUSTOM Steps 01, 02 and 03, and the parent = children + unallocated rule.
4 Material Request approval workflow and a WBS budget check on each line STANDARD CUSTOM T2, T3. The workflow is configuration; the budget check is custom code.
5 Rewrite the budget reports to roll up the tree and show committed, in stock and consumed side by side, in quantity and amount CUSTOM R1, R3, R4, R5.
6 Contract value on the BOQ; link the Procurement Plan to allocations and Material Requests CUSTOM The contract-vs-budget split, A5, T5.
Standard configuration vs customisation Only the Accounting Dimension and the Material Request workflow are standard ERPNext configuration. Everything else on this list needs custom work in A3 Constructa.
